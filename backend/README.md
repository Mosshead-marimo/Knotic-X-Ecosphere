# Backend

Python service boundary for Flask APIs, session management, Agora token generation, service composition, and LangGraph orchestration.

The Python namespace is `knotic_api`; the process entry point is `knotic_api.__main__:main`. Python, uv, Flask, LangGraph, state/database clients, and the MCP client are locked at the workspace root. Startup validates required configuration before serving the Flask application.

Persistence code lives under `knotic_api.persistence`. PostgreSQL is durable authority and is changed only through Alembic. Redis holds a rebuildable, size-bounded `SalesState` projection with environment/tenant/session key isolation, a sliding TTL, schema and event watermarks, atomic optimistic updates, and lease fencing. Redis misses or corrupt values require hydration from PostgreSQL; Redis outages fail explicitly and never imply a successful write.

All durable application writes run inside `UnitOfWork`, which opens one short PostgreSQL transaction and sets trusted tenant/actor context before exposing typed repositories. Repositories repeat tenant predicates even with forced RLS. External calls are forbidden inside this boundary; reserve idempotency, write business state plus events/outbox work, commit, and only then invoke providers.

Structured memory updates are pure domain operations in `knotic_api.domain.memory`. Current facts retain confirmation, confidence, actor, source-turn, capture-time, and version provenance. Confirmed values cannot be displaced by tentative extraction, same-turn conflicts fail closed, and accepted facts are projected into typed customer, requirement, competitor, topic, next-action, and objection state rather than relying on raw transcript text.

Objection detection is a pure workflow boundary covering the exact nine FR-07 categories. Its reviewed policy grounds pricing, comparison, and capability responses; asks discovery questions where facts are missing; and escalates security, legal, trust, or otherwise high-risk claims. Current objection state preserves first/latest turns and versions, while immutable evidence rows retain exact offsets, hashes, confidence, risk flags, and policy decisions without storing plaintext evidence.

Qualification is a pure FR-09 policy over confirmed structured memory and validated explicit intent. Every calculation carries all seven bounded dimensions, evidence/missing-data codes, the previous score, and any explicit-request stage override. Numeric scores always retain their evidence-derived value; booking, demo, follow-up, and closing requests may override only the stage, with turn provenance and a closed reason code. Replays of the same source turn do not duplicate qualification history or events.

Next-best-action selection is a deterministic FR-10 decision table. Decisions carry a closed reason, required and missing inputs, the exact governed MCP boundary, approval level, grounding requirement, provider-confirmation requirement, and safe fallback. Booking is never executable without both a selected slot and bound customer confirmation, and it can never be described as successful until the calendar result is provider-confirmed. High-risk objections preempt ordinary routes with a policy-governed handoff.

Response generation separates deterministic planning from model phrasing. Plans accept only typed, server-validated facts with source metadata, select at most four voice-oriented talking points, and use deterministic uncertainty language when required grounding is absent. Transactional actions use fixed pre-confirmation language, closing remains silent, and output validation rejects unknown citations, ungrounded prices/capabilities, long responses, and unconfirmed success claims. The OpenAI adapter uses stateless structured output and excludes raw customer content from its generation payload.

Workflow turn execution uses a tenant/session/turn-unique PostgreSQL checkpoint ledger with forced RLS, a bounded lease, one-to-three attempts, deterministic committed/terminal states, and authenticated AES-256-GCM state encryption. The executor retries only failures explicitly marked retryable, converts deadlines and unexpected exceptions to user-safe failures, resumes expired/retryable leases, and returns committed or terminal replays before graph invocation. The synchronous LangGraph adapter runs in a bounded shared worker pool; provider calls retain their own tighter deadlines.

LangGraph orchestration lives under `knotic_api.workflow`. Its versioned state binds every run to a tenant/session-derived checkpoint identity, and every node has a declared pure-or-I/O boundary plus an allowlist of fields it may mutate. The Phase 2 graph compiles from this contract inventory; model calls and business side effects enter only through later typed adapters and governed nodes.

Turn understanding uses the provider-neutral `TurnUnderstandingPort`. The production adapter calls the OpenAI Responses API with `gpt-5.6-terra`, non-retained requests, bounded timeouts, low reasoning effort, and a strict Pydantic structured-output schema. Customer text is serialized as explicitly untrusted data. The model may propose only customer-supplied fields; it cannot propose current topic, next action, tools, or business outcomes. Trusted source-turn and provider-response provenance are attached by the adapter after validation.

The `update_memory` graph node is deterministic and performs no provider access. Explicit, unambiguous entity proposals at or above the approved confidence threshold enter the existing structured-memory merge policy; inferred, ambiguous, and low-confidence values are retained as typed uncertain claims and cannot overwrite confirmed facts. Accepted changes receive deterministic replay-safe UUIDv7 identities, update the checkpoint state/event watermarks, and emit `requirement.updated` or `memory.updated` envelopes with old/new values and source-turn provenance.

Intent routing is a closed deterministic matrix from every FR-06 intent to one approved LangGraph branch. `CONTINUE`, `SWITCH`, and `RETURN_PREVIOUS` topic controls operate on a typed, 32-frame bounded history. Ambiguous turns and impossible return requests route to clarification without destroying history. Every branch rejoins the workflow before qualification, and branch nodes remain side-effect-free until their dedicated implementation task.

Confirmed requirement revisions are serialized by the owning session row. Replacing `requirements_current`, appending immutable old/new history, and emitting the ordered `requirement.updated` event occur in the same `UnitOfWork` transaction. Source-turn replays return the original event without adding history; conflicting replays and stale concurrent versions fail closed. Revision and event rows retain actor, source, causation, and correlation metadata.

`SalesStateHydrator` is the Redis-first state loading boundary. A miss or corrupt value is reconstructed under a tenant-scoped durable lock from session, lead, requirement/history, objection, competitor, qualification, outcome, and event-watermark rows; encrypted fields are authenticated with purpose-separated AES-256-GCM before entering state. Cache warming is create-only and race checked. Checkpoints use durable optimistic versions and cannot advance past immutable event history. Legacy pre-watermark cache envelopes are atomically migrated in place, and recovery never appends events.

Privacy operations live in `knotic_api.privacy` and follow `docs/DATA_LIFECYCLE.md`. Exports, erasure requests, provider-confirmed deletion, legal holds, bounded retention, and housekeeping are tenant scoped and auditable. Erasure requests install a Redis privacy tombstone that active-state hydration treats as a hard processing block. Operational application logs install `SensitiveDataFilter`. Database migration `20260822_0005` defines non-login runtime, retention, and auditor roles without RLS bypass.

The `/api/v1/sessions` create/read/end lifecycle is registered by the Flask factory. Browser access requires an opaque `knotic_session` backed by Redis; mutations additionally require an allowed exact origin, the session-bound CSRF token, and an idempotency key. Rate limits fail closed. Idempotent response bodies are encrypted with AES-256-GCM, and request/correlation identifiers appear in every API response. OIDC routes minting browser sessions are a separate contract implementation; until those routes exist, no production client can self-issue an authenticated cookie.

Settings are defined in `knotic_api.config`; shared provider and redaction primitives live in `packages/config`. See `../docs/CONFIGURATION.md` and the root `.env.example`.

External business integrations must be accessed through the MCP boundary. Follow `../docs/AGENTS.md` and `../docs/COMPONENT_OWNERSHIP.md`.
